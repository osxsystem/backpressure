Architecture  ·  v0 blueprint

You don't build the agent. You build the backpressure.

A shareable toolkit that installs into existing agentic coding CLIs — Claude Code and Codex — and makes their autonomous loops converge instead of drift. Skills, hooks, subagents, an issue tracker, third-party tools, and a Ralph loop, authored once and compiled to each CLI's native format.

ralph.sh — the whole idea
# state lives on disk, not in context
while task = tracker.next(); do
  $CLI exec "$(render $task)"   # fresh context
  run_tests && git commit         # backpressure
  tracker.update $task
done   # you sit ON the loop, not IN it
01 — The model

A capability pack, not a runtime

Your unit of value is configuration, prompts, and small scripts installed into a harness someone else maintains. The agent loop, tool execution, context management, and sandboxing belong to the CLI. The decisive advantage: as of 2026, Claude Code and Codex CLI have converged on the same five extension primitives plus a plugin-packaging concept — so a single source of truth can target both.

Project instructions both

CLAUDE.md / AGENTS.md — persistent guidance loaded before any task.

Hooks both

PreToolUse, PostToolUse, Stop, SubagentStop, PreCompact — same event model, different config file.

Subagents both

Isolated-context specialists the main agent delegates to. Markdown on one side, [agents] on the other.

Skills both

Markdown capability bundles loaded on demand — largely portable as-is.

MCP servers both

The same protocol both CLIs speak. 100% portable — config only, zero adapter.

Plugin bundle both

Both wrap skills + hooks + MCP + connectors into one installable package.

Codex even ships an /import that migrates setup and config from Claude Code — the surfaces are that close.

The dependency spine

These six aren't peers. The issue tracker and Ralph loop are the core you design first; the capabilities are backpressure you add reactively to make the loop reliable.

01
Select

Loop asks the tracker for the next open task with machine-checkable acceptance criteria.

02
Execute

CLI runs headless on one task with a fresh context window and the installed capabilities.

03
Gate

Hooks enforce scope and refuse to "succeed" on a red build; subagents review in isolation.

04
Persist

Tests pass → git commit. State survives the context wipe on disk + git, never in chat history.

05
Write back

Tracker marks done / blocked / spawns follow-ups. Loop restarts clean. Repeat until empty.

03 — Tech stack

Lean by design

A capability pack should be small. TypeScript on Node for the installer, adapters, and MCP servers; a deliberately dumb shell harness for the loop; everything CLI-specific hidden behind one seam.

04 — Roadmap

Build the spine, then the backpressure

Design and ship in dependency order. Each phase has one goal and a hard exit criterion — don't advance until it's met. Backpressure is added reactively, never pre-built.

05 — Principles & risks

Rules that keep the loop honest

Ralph loops shine on greenfield work with testable outputs and clear requirements; they struggle on large legacy code that needs human navigation. Design around that.

01

Cap cost & iterations from day one

Uncapped loops are the fastest way to a huge bill. The governor is not a Phase 5 feature — it's a Phase 0 line.

02

State must survive a fresh context

Every iteration wipes the window. Anything not in git, the tracker, or a file on disk is gone. Design state to live where the loop can re-read it.

03

Make acceptance criteria machine-verifiable

A passing test or clean lint is what lets the loop self-correct without you in the chair. Write the tracker's criteria field to be checkable.

04

Add backpressure reactively

Don't pre-build a library of hooks and skills. Watch the loop fail, fix that failure class, repeat. Sit on the loop, not in it.

05

Keep CLI-specifics behind one seam

If you've classified portability tiers right, "which CLI" is a packaging detail — it should touch exactly one module.

06

The tracker and the loop are one design

The loop has no memory of its own; the tracker is its queue and its memory. Design their contract together, before anything else.
