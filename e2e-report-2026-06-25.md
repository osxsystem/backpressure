## Phase 3 — Error handling

### 3.1 Missing `skills/` in cwd — PASS (design changed; issues/001 & /003 resolved)

```
$ cd <empty temp dir>            # no skills/ directory
$ node dist/cli.js init --target claude
Wrote: …/.claude/settings.json
Wrote: …/.mcp.json
Wrote: …/.claude/agents/reviewer.md
Wrote: …/.claude/skills/building-adaptive-ui/SKILL.md   (exit 0)
```

The E2E prompt expected a clean error here. **It no longer applies.** Per the User
Guide, `init` now reads bundled skills from the *pack's own install location*
(`bundledSkillsDir()`), not from `<cwd>/skills`, "so you can run it from any repo."
Running in a repo with no `skills/` therefore *correctly* succeeds. This is exactly
the fix that closes `issues/001` (raw ENOENT crash) and `issues/003` (dry-run
green-lighting a doomed real run). Both issues are **resolved** by this design.

### 3.2 Dry-run vs real consistency — PASS

In the no-`skills/` dir, both `--dry-run` and the real run succeed with identical
4-file plans. They agree on success/failure (the defect `issues/003` describes is gone).

### 3.3 Unknown target — **FAIL (real defect)** → ✅ RESOLVED (2026-06-29)

> **Resolved.** `parseTarget` now throws an `InstallError` and is called *inside*
> every subcommand action's try/catch, so a mistyped `--target` prints one clean
> `backpressure: unknown target "…"` line on stderr (exit 1, no stack). Pinned
> end-to-end by the `clean CLI errors end-to-end` regression tests in
> `test/cli.test.ts`, which drive `parseAsync` for `init`/`build`/`index`/`remove`
> — guarding the exact wiring this finding flagged (the unit was already fine).



```
$ node dist/cli.js init --target bogus
file:///…/dist/cli.js:487
  throw new Error(`Unknown target "${value}". Expected one of: ${TARGETS.join(", ")}.`);
        ^
Error: Unknown target "bogus". Expected one of: claude, codex.
    at parseTarget (file:///…/dist/cli.js:487:9)
    at Command.<anonymous> (…)
    … 8 more stack frames …
Node.js v22.22.2
exit code: 1
```

- **Expected** (E2E prompt 3.3 + the `backpressure: <message>` contract the guide
  establishes for clean failures): a single-line `backpressure: Unknown target …`
  on stderr, non-zero exit, **no stack trace**.
- **Actual:** correct message text, valid targets listed, exit 1 — **but emitted as
  an uncaught exception with a full Node stack trace.** `parseTarget` throws during
  Commander's option parsing, before the action handler's try/catch.
- **Severity:** Low–Medium. The message is informative and the exit code is right,
  but the presentation is the same "fails ugly" class of bug that `issues/001` was
  filed for — and a typo'd `--target` is one of the most common user errors. The
  fix is in scope of the same hardening that cleaned up the other error paths.

For contrast, the **unknown-skill** path is handled cleanly:

```
$ node dist/cli.js init --target claude --skill does-not-exist
backpressure: skill "does-not-exist" is not bundled. Available: building-adaptive-ui, skill-creator
exit code: 1   (nothing written)
```

This is the exact shape the unknown-target path *should* have.
